## 3. 機能をまたぐ受け渡し仕様

型の定義は [`lib/core/photo/`](../lib/core/photo/) を参照する。担当ごとに別の受け渡し型を作らず、変更が必要なら利用する担当者と先に相談する。

```text
撮影画像のバイト列
  → PhotoProcessor.normalize → SourcePhoto
  → 編集画面で List<HideRegion> を選ぶ
  → PhotoProcessor.redact → RedactedJpeg
  → PhotoSaver.save → SaveResult
```

### 画像と座標

- `SourcePhoto` は向きを画素に反映し、EXIF などのメタデータを除いた画像。#19 では撮影後に JPEG を再エンコードする方針を採用している。
- `SourcePhoto.width`・`height` は正規化した後の画素サイズ。EXIF 正規化で縦横が入れ替わる場合も、このサイズを座標の基準にする。
- `HideRegion` はその画像の左上を原点とする整数の画素座標。`right`・`bottom` は範囲に含まない。
- 画面の論理ピクセルから画像の画素座標への変換は #9 が担当する。実際の画像表示位置・余白・縮尺を使い、画像の外には範囲を作らない。
- `HideRegion.fromRect` は逆向きのドラッグ、画像外の切り取り、外側への丸めを扱う。画像と重ならない場合などは `null` を返す。
- #10 は同じ `SourcePhoto` と `List<HideRegion>` から、元と同じ画素サイズの `RedactedJpeg` を生成する。黒塗りは不透明な画素として焼き込み、元画像の EXIF や未加工のサムネイルを含めない。
- 将来の顔・文字検出も、この正規化済み画像を基準に `HideRegion` を返す。検出用に縮小した場合は元の画素座標に戻す。
- 画像のバイト列は受け取り側で書き換えない。加工結果は新しい画像として返す。

### 保存と編集状態

- `PhotoSaver.save` の入力は `RedactedJpeg`。未加工の撮影ファイルをそのままギャラリーへ渡さない。
- 保存結果は既存の `SaveSucceeded` または `SaveFailed`。失敗理由は `permissionDenied` と `failed` が定義されている。
- 保存前確認から編集へ戻る場合と保存に失敗した場合は、`SourcePhoto` と選択範囲を保持する。
- 保存中は重複操作を防ぐ。成功を確認してから成功表示し、「もう一枚」で撮影へ戻る。

### 一時ファイルとプライバシー

- 画像・画像内の情報を外部へ送信せず、ログに画像や個人情報を含めない。
- 現在は `CapturedPhotoScreen.dispose` で撮影ファイルを削除し、次回起動時にも残った撮影ファイルを削除する。
- 画面の分割時には、正規化処理が読み終える前に元ファイルを消さないことと、撮り直し・終了時に不要なファイルが残らないことを確認する。
- 画像の所有と破棄のタイミングは #9・#10・#12 で共有する。複数の画面で別々の編集状態を持たない。

## 4. 分担開始時に決めること

共通型だけでは次の事項は決まっていない。該当する担当者間で決め、Issue または PR に記録する。

| 事項 | 関係する担当 | 共有する内容 |
| --- | --- | --- |
| 担当とレビュー | 全担当 | 実装担当、レビュー担当、結合・実機確認担当。未確保の検証端末も記録する |
| 画面への接続 | #9・#10・#12 | `normalize` の呼び出し位置、処理インスタンスの渡し方、`XFile` の確認画面から編集画面への切り替え方 |
| 正規化・加工の失敗 | #9・#10・#12 | `PhotoProcessor` の例外の扱い、表示するメッセージ、再試行時に保持する状態。保存用の `SaveResult` はすでに定義済み |
| 共有ファイルの変更 | 関係する担当 | 共通型、`camera_screen.dart`、`captured_photo_screen.dart`、`pubspec`、Android 設定を変更する場合の担当範囲とマージ順 |
| MVP の確認待ち項目 | プロダクトの判断担当・#9・#15 | 定義書第 12 節の黒塗り・デモ環境・サンプル画像の状態を更新する。#9・#15 は黒塗り・同梱サンプルを前提に書かれている |
| 説明文の整合性 | 配布・文書担当 | `scripts/beta_release.py` の Release 説明には旧起動画面の記述が残る。撮影できる現在の範囲に合わせる |

## 5. 作業中に共有すること

Issue の開始時に、次を短く記録する。

```text
実装担当 / レビュー担当 / 結合確認担当:
変更する主なファイル:
着手に必要なもの:
完了確認に必要な Issue:
他の担当へ渡すもの（型・画面・処理・確認用画像）:
確認する端末・OS / 未確認の環境:
```

共通仕様や利用する型を変える場合は、実装を進める前に関係する Issue に変更案と影響を書いて相談する。
PR には変更内容・確認方法・未確認事項・結合に必要な後続作業を記載する。

## 6. 結合・レビュー・配布で共有すること

- 通常の確認コマンドは `mise run check`。カメラや保存など Android 固有の変更は実機でも確認する。
- 結合確認では、縦・横・前面カメラの写真、画像の端と余白、複数領域と取り消し、保存失敗時の状態保持を確認する。
- 画像処理ではプレビューと保存画像の黒塗り位置、画素サイズ、EXIF と未加工のサムネイルの除去を確認する。
- 端末・OS・対象コミット・実施日・結果・制約は [検証記録](verification.md) に残す。記録済みのカメラ確認と、今後の編集・保存の確認を混同しない。
- 別メンバー 1 人以上がレビューし、必要な CI の成功を確認して main へマージする。main へのマージでベータ版が自動公開される。
- 通常 CI でエミュレーターは起動しない。端末テストは `device-test` ラベルまたは手動実行、デモ APK は手動実行または Android ビルド設定を変える PR で実行する。
- 署名鍵の保管責任者を決め、[ベータ版の運用](beta-releases.md)に沿ってバックアップする。鍵とパスワードは Issue・PR・Git に載せない。
- 最後は [MVP 定義書の完了条件](mvp-definition.md#10-mvp-の完了条件)に沿って、撮影から保存、オフライン動作、他メンバーによるデモ再現まで確認する。
