# camereon MVP 定義書

状態: 確認待ちの初稿。第 12 節の回答を反映して確定する。

2026-10-13: 最初の実装は「起動画面・テスト・両 OS の起動確認・Android のみ配布」に絞る。
今回の範囲と完了条件は [起動・検証・Android 配布の定義](bootstrap-definition.md) を優先する。
以下は撮影・加工・保存までを含むプロダクト全体の MVP 定義であり、今回の基盤実装とは分けて扱う。

関連 Issue: [#1 定義書作る](https://github.com/camereon-dev/camereon/issues/1)

## 1. エレベーターピッチ

camereon は、写真を SNS に投稿する前に、写り込んだ個人情報を簡単に隠せるカメラアプリ。
撮影した写真の気になる場所を指で選び、隠して、加工済みの画像を端末に保存できる。
画像は端末内で処理する。まずは手動で確認・加工できる体験を作り、将来は危険箇所の自動検出を加える。

## 2. 対象ユーザーと課題

対象は、日常の写真を SNS に投稿する人。
背景の住所、名札、書類、顔などの写り込みを確認する手間と、別の加工アプリで隠す手間を減らす。

MVP で確かめたいことは「撮影から保存まで迷わず進めて、複数の写り込みを手軽に隠せるか」。
自動検出の精度や、情報漏えいを完全に防げるかは MVP の評価対象にしない。

## 3. 開発方針

- iOS・Android に対応する Flutter アプリを、同じリポジトリで開発する。
- 撮影・領域選択・加工・保存を一続きで使えるようにする。
- アプリに加えて、他のメンバーが再現できるデモ環境を作る。
- ログイン、バックエンド、外部の画像処理 API は不要とする。
- UI は日本語。MVP の操作画面は縦向き固定でよい。横向きに撮影した写真も正しく表示・保存する。

## 4. MVP の機能

以下の黒塗りとサンプル画像は、確認待ちの提案。

| 機能 | 必要な動作 |
| --- | --- |
| 撮影 | 背面カメラのプレビューから 1 枚撮影し、編集画面へ進める。撮り直しができる |
| サンプルを開く | 同梱した架空の個人情報を含む画像から、カメラなしで編集のデモができる |
| 領域選択 | 指でドラッグして長方形を作り、複数箇所を選べる。画像の外には領域を作らない |
| 隠す | 選んだ範囲を不透明な黒で塗りつぶす。操作後すぐに加工結果を表示する |
| 取り消し | 最後の領域追加を取り消せる。すべての選択をリセットできる |
| 保存前確認 | 加工済み画像を確認して保存できる。編集へ戻っても選択を保持する |
| 保存 | 加工済み画像を、iOS の写真ライブラリ／Android のギャラリーに新しい画像として保存する |
| 結果表示 | 保存成功と失敗を区別し、失敗時は選択を保持して再試行できる |

長方形の移動・サイズ変更、拡大縮小は MVP 必須にしない。選び直す場合は取り消して再選択する。
カメラ切り替え、フラッシュ、動画、既存の写真の読み込みも MVP 必須にしない。

## 5. 操作の流れ

1. 起動画面で「撮影する」または「サンプルで試す」を選ぶ。
2. 撮影する場合は、カメラの権限を求めて撮影する。
3. 編集画面で、隠したい場所をドラッグする。別の場所も追加できる。
4. 「保存前に確認」で加工結果を見る。
5. 「写真に保存」で必要な権限を求め、加工済み画像を保存する。
6. 成功したことを表示する。「もう一枚」で最初へ戻れる。

編集を破棄して戻る場合は確認する。保存中は重複操作を防ぐ。
保存前確認画面には「隠し忘れがないか確認してください。安全を完全に保証するものではありません。」と表示する。

## 6. 画像処理とプライバシー

- 撮影・表示・加工・保存は端末内で完結させる。インストール後はオフラインでも利用できる。
- 元画像、加工済み画像、画像内の情報を外部へ送信しない。画像をログやクラッシュ情報に含めない。
- 未加工の撮影画像は写真ライブラリへ自動保存しない。アプリ内の一時ファイルは不要になった時点で削除する。
- 編集状態はセッション中だけ保持し、アプリ終了後の編集復元は MVP に含めない。異常終了で残った一時ファイルは次回起動で削除する。
- 保存画像には黒塗りを画素として焼き込む。元の画素を下層や別ファイルとして含めない。
- 保存画像は JPEG とし、画面のスクリーンショットではなく元画像の画素サイズで生成する。
- 画像の向きを正規化し、位置情報、撮影日時、端末情報など元画像の EXIF を保存画像に引き継がない。
- 表示サイズと元画像サイズの座標を変換し、プレビューと保存画像で隠す位置を一致させる。
- 写真へのアクセスは保存に必要な範囲に限定する。権限拒否時にアプリが落ちず、設定変更の案内や再試行ができる。

アプリが元画像を外部送信しないことは、端末の写真ライブラリに対する OS やユーザー設定のクラウド同期まで制御する意味ではない。

## 7. MVP に含めないもの

- OCR・画像認識による危険箇所の自動検出
- ユーザーごとの公開可能な情報の設定
- モザイク、ぼかし、スタンプ、画像への置き換え（隠し方の回答次第で変更する）
- 人物をアバターに置き換える
- SNS への直接共有
- アカウント、サーバーへのアップロード、広告、利用分析
- App Store／Google Play での一般公開

自動検出を追加する際も、検出で安全を完全に保証できないことと、ユーザー自身の確認が必要なことを明示する。

## 8. デモ環境も成果物にする

以下は回答前の推奨案。TestFlight 配布の要否は第 12 節で決める。

| 対象 | 成果物と確認内容 |
| --- | --- |
| Android | ダウンロード・インストール可能なデモ APK。実機で撮影からギャラリー保存まで確認する |
| iOS | macOS・Xcode・iOS Simulator で起動できる手順。実機で撮影から写真ライブラリ保存まで確認する |
| カメラがない環境 | 同梱サンプルから複数領域を隠し、保存まで操作する |
| 再現手順 | SDK とツールのバージョン、前提、コマンド、権限設定、配布物の場所、困ったときの対処を README に記載する |

iOS のビルド・Simulator 起動には macOS と Xcode が必要。実機へのインストールには署名設定が必要。
TestFlight での配布を選ぶ場合は、Apple Developer Program と App Store Connect の準備・アップロード・配布までを追加の完了条件とする。
Simulator のサンプル操作だけでは、iOS の実機撮影の完了とはしない。

同梱画像は架空の住所・名札などを使い、実在の個人情報を含めない。利用許諾もリポジトリに記録する。
デモ手順は「サンプルを開く → 2 箇所を隠す → 1 回取り消す → 保存 → 写真アプリで確認」を基本にする。
開発環境を導入済みの別メンバーが、手順だけで 15 分以内に起動できることを目標にする。

参考: [Flutter の導入](https://docs.flutter.dev/install)、[Android ビルドと配布](https://docs.flutter.dev/deployment/android)、[iOS ビルドと配布](https://docs.flutter.dev/deployment/ios)。

## 9. チームで開発するための準備

- Flutter SDK の採用バージョンを固定し、固定方法と更新手順を README に書く。アプリの依存ロックファイルを共有する。
- `main` を共有の基準とし、タスクごとのブランチと PR で変更する。原則、別メンバー 1 人のレビューを受ける。
- GitHub Actions でフォーマット確認、静的解析、テスト、Android ビルド、iOS Simulator ビルドを実行する。iOS は macOS runner を使う。
- 画像座標変換、黒塗りの出力、編集状態の取り消しを自動テストの対象にする。カメラ・権限・写真保存は両 OS の実機でも確認する。
- カメラ入力、編集状態と画像処理、保存処理、画面 UI を分ける。OS 固有の処理は入出力側に置く。
- 入力は画像のバイト列と正規化した画素サイズ、選択範囲は元画像上の長方形、出力は加工済み JPEG とする。受け渡しの型は最初の基盤 PR で決める。
- 署名鍵、証明書、パスワード、個人の設定を Git に追加しない。CI で必要な認証情報は Secrets で管理する。
- Issue ごとに担当者、依存タスク、完了条件を付ける。結合・両 OS の確認・デモ配布も担当を決める。

推奨するタスク分割:

| 順序 | タスク | 完了条件 |
| --- | --- | --- |
| 1 | Flutter 基盤・環境・CI | サンプル画面が両 OS で起動し、共通の型と起動手順を共有できる |
| 2 | 画像入力 | 実機撮影と、採用する場合は同梱サンプルから編集へ画像を渡せる |
| 2 | 編集・画像処理 | 長方形を複数追加・取り消しでき、加工済み JPEG を生成できる |
| 2 | 保存 | OS ごとの権限と保存を扱い、成功・失敗を呼び出し元へ返せる |
| 3 | 結合・デモ | 操作の流れを結合し、両 OS 実機の確認記録と配布物・手順を揃える |

画像入力・編集・保存は基盤とインターフェースを合意したあと、担当を分けて進められる。

## 10. MVP の完了条件

以下をすべて満たした時点で MVP 完了とする。回答によってデモの条件を更新する。

- [ ] iOS・Android の実機で、撮影 → 複数領域を隠す → 保存前確認 → 保存を完了できる。
- [ ] 最後の領域の取り消し、全リセット、撮り直し、編集への戻りが仕様どおりに動く。
- [ ] 縦・横の写真、表示の余白、画像の端、重なる領域で、プレビューと保存画像の黒塗り位置が一致する。
- [ ] 保存画像を標準の写真アプリで開ける。元画像の画素サイズを保ち、選択範囲は不透明な黒で焼き込まれている。
- [ ] 保存画像に元画像の EXIF、元の画素を含むレイヤー、未加工のサムネイルが残っていない。
- [ ] カメラや保存の権限を拒否しても落ちず、再試行や設定変更の案内ができる。
- [ ] カメラが利用できない場合、保存に失敗した場合に理由を表示し、可能な操作を案内できる。
- [ ] 保存に失敗しても編集状態を保持し、成功したと誤表示しない。
- [ ] ネットワークを切った実機でも一連の操作ができ、画像を外部送信する処理がないことをレビューで確認している。
- [ ] 未加工画像を写真ライブラリへ自動保存せず、一時ファイルの削除が確認できる。
- [ ] 保存前に、隠し忘れの確認と安全を完全に保証しない旨の文言が表示される。
- [ ] 同梱サンプルによるデモができる（採用する場合）。
- [ ] Android APK と iOS の合意したデモ環境・手順が揃っている。
- [ ] 別メンバーが README の手順で起動し、デモ手順を最後まで再現できる。
- [ ] CI が成功し、確認したコミット、OS・端末、実施日、結果、既知の制約を記録している。

## 11. Issue #1 の完了条件

MVP 実装の完了とは分けて、定義書の Issue は次の条件で完了する。

- [x] コンセプト、対象ユーザー、課題、エレベーターピッチが書かれている。
- [x] MVP の範囲、画面の流れ、画像処理、プライバシーのルールが書かれている。
- [x] デモ環境とチーム開発の進め方を含めた完了条件が書かれている。
- [ ] 第 12 節の回答を反映し、確認待ちの記述を確定する。
- [ ] チームが定義書を確認し、基盤・入力・編集・保存・結合とデモの実装タスクに分割できる。

## 12. 決めること

| 決定事項 | 推奨案 | 状態 |
| --- | --- | --- |
| 隠し方 | 複数の長方形を黒塗りする。取り消し可能 | 回答待ち |
| デモ環境 | Android APK ＋ iOS Simulator 手順 ＋ 両 OS の実機確認。TestFlight は今回必須にしない | 回答待ち |
| サンプル画像 | 架空の個人情報を含む画像を同梱する | 回答待ち |

採用する Flutter SDK、最低対応 OS、検証端末、担当者は基盤タスクの開始時に決め、README に記録する。
最低対応 OS は採用 SDK とカメラ・保存用プラグインの対応範囲を確認して固定する。
両 OS の実機と、iOS をビルドできる Mac を確保できない場合は、実機検証の完了条件を満たせないため、着手時に共有する。
