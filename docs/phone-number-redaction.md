# 日本の電話番号を住所・顔と同じ操作で隠す

## 動作

既存の日本語OCR結果を住所・郵便番号・電話番号で共有する。Androidは同梱ML Kit、iOSはApple Visionを引き続き利用し、電話番号の形式とラベルの判定は共通Dartコードで行う。電話番号専用のOCR、外部API、モデル、依存パッケージは追加しない。

- 日本の固定電話などの10桁、050/060/070/080/090などの11桁、0120/0570/0800、国番号+81の表記を対象にする。桁数だけでなく先頭番号と区切りも確認する。
- 全角数字・記号、空白、ハイフン、国内の括弧付き市外局番、+81 (0)表記を正規化する。OCRが誤読したOを0に置き換えるなどの推測はしない。
- 完全な形式に一致した番号は、住所・郵便番号・顔と同様に初期選択して隠す。
- 「電話番号」「電話」「携帯」「TEL」「PHONE」「連絡先」の直後、または近接した直下にある7〜8桁のローカル番号は候補にするが、自動では隠さない。数字だけの短い列は候補にしない。
- 管理番号・注文番号・ID・FAXなど、別用途のラベルが直前にあるものは対象外。長い数字列の一部分、日付、郵便番号、英数字IDやメールに埋め込まれた数字を電話として拾わない。
- 「電話番号」の枠や種類ボタンで解除・再適用できる。取り消し、撮影後の確認、写真選択、保存・共有は既存処理を使う。再検出は種類ごとに既出範囲を照合し、利用者が表示へ戻した番号を勝手に隠し直さない。
- 保存前の待機と不透明な仮マスクは既存処理を使う。ラベル・氏名・住所を電話枠へまとめず、認識された番号の文字座標を結合し、OCR枠外に残る数字の端を覆うため文字高さの15%（最低2px）の余白を付ける。

## グループ開発で共有する変更

- `CandidateKind.phone`を追加する。既存の`SourcePhoto`、`HideRegion`、`PhotoProcessor`、`PhotoSaver`、ネイティブMethodChannelの契約は変更しない。
- `JapaneseAddressDetector.detect`は同じOCR呼び出しから住所と電話の両方を返すようになる。`japaneseAddressCandidates`単体の住所ルールと地名辞書は変更しない。結果を住所だけと仮定している呼び出し側は種類で絞り込む。
- 新規`PhoneNumberCandidate.automaticallySelected`は電話候補の初期選択を表す。既存`RegionCandidate`のコンストラクタは変更しない。
- ラベル付き7桁ローカル番号と郵便番号候補がほぼ同じ範囲になった場合だけ、電話の未選択候補へまとめる。`TEL:123-4567`を郵便番号として自動マスクしないための限定的な優先順位であり、通常の郵便番号候補は維持する。
- 通常の編集画面は住所と電話の両方を受け取り、電話用ボタンを表示する。選択履歴と再検出の既出管理を種類別にする。
- Android/iOSのネイティブコード、ビルド設定、依存ファイル、モデル、GitHub Actionsは変更しない。mainで削除されたONNX/Gemma/旧検出器を復活させない。
- 既存の住所端末テストは電話が保存JPEGにも隠れる新仕様へ更新する。

## 限界

実際に割り当てられた番号か、つながる番号かは検証しない。ラベルなしの管理番号が電話番号と同形式の場合は誤候補になり得る。辞書や通信による本人・契約者照合は行わない。

電話番号が複数の行に分かれている場合、短縮番号・内線・日本以外の国番号は今回の対象外。OCRが文字を読み落とした場合は検出できない。離れた欄は結合しない。同じ行で複数の番号が区切りなしに続く場合も見落とすことがある。

Androidの合成画像テストでは、住所辞書が「電話番号」「管理番号」などのラベルの一部も地名として隠す既存の挙動を確認した。電話候補は数字部分だけだが、住所候補として別に隠れる場合がある。今回は住所辞書・ルールの変更を対象にしない。

iOSの文字矩形はVisionが単語単位で返す場合があり、番号だけの厳密な切り抜きは実機で確認する必要がある。住所検出はmainの辞書・ルールをそのまま使うため、地名と一致した氏名や一般語を住所候補として隠す既存の挙動も変わらない。

## テスト

- 形式・全角・+81・ラベルの右/直下・距離・別段組・不正桁数・日付・郵便番号・管理番号・メール・番号部分の座標を単体テストする。
- モックOCRで、1回の呼び出しから住所・郵便番号・電話の候補が得られることを確認する。
- 編集画面で自動選択と未選択候補、タップの往復、種類ボタン、取り消し、再検出後の解除維持、撮影後の確認と保存範囲を検証する。
- 実OCRは既存`parcel_ja.png`と、電話番号・ラベル・管理番号・日付・郵便番号・公開住所を描いた合成画像で検証する。実在する個人の連絡先は使用しない。
- Android端末テスト: `flutter test integration_test/japanese_phone_number_device_test.dart -d <device-id>`。JPEGの画素で電話の文字が消え、解除/未選択の対象や番号以外が残ることと、写真ライブラリ保存を確認する。

## 検証結果（2026-11-17）

- Flutterの全290テストが成功。静的解析も問題なし。
- Android 17 / API 37 / arm64エミュレーターで、既存配送ラベルと合成画像の実OCR・編集・JPEG保存の2テストが成功。
- 機内モードを有効にし、Wi-Fi・モバイルデータを無効化、既定ネットワークなしを確認して実行した。終了後は通信設定を元に戻した。
- 合成画像では電話4件が自動選択され、ラベル付きローカル番号2件が未選択候補になった。描画時の番号全体の座標に対する画素検査で、保存JPEGに数字の端が残らないことを確認した。未選択の番号、管理番号、日付、英語のサンプル氏名の値は残り、郵便番号は隠れた。
- 既存の住所端末テストも1件成功。住所・電話の解除／再適用と保存を確認した。氏名の保存検証には地名辞書と衝突しない英語のサンプルを使用した。
- iPhone実機と一般実写写真での網羅的な精度評価は未確認。合成画像と既存サンプルの成功を一般的な検出精度として扱わない。

画像・実行環境・検証記録は[検証資料](evaluation-evidence/2026-11-17-phone-numbers/README.md)を参照。
